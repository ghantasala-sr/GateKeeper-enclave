# Drill: point-in-time restore (Module C3)

**Date:** 2026-10-23 · **Release:** 0.1.4 · **Script:** [`proof/restore-drill.sh`](../../proof/restore-drill.sh)
**Targets:** RPO 15 minutes, RTO 1 hour · **Result: passed** (RPO about 5 seconds, RTO 24 minutes)

## Scenario

An operator deletes every chunk of one document (`ACME-HR-01`, Acme's salary bands) in production by mistake.
The document still exists, but nobody can retrieve it any more.

- **RTO:** 24 minutes, against a 60-minute target. Nearly all of it was Cloud SQL creating the clone; the
  verification and the repair took 24 seconds.
- **RPO:** the data came back as of 5 seconds before the incident (point-in-time recovery replays the
  write-ahead log), against a 15-minute target.

## How it ran

Every database step ran **inside** the Enclave, as a Job on GKE, labelled like the setup Job so the
NetworkPolicies allowed the database and nothing else. The Job used the owner login from the Kubernetes Secret.

The operator laptop issued only the Cloud SQL admin calls: clone and delete. The bastion deliberately can't make
those. The owner is not a superuser on Cloud SQL, so every step ran inside Acme's row-level-security context,
like the app's own setup scripts.

The repair copied the lost rows back rather than switching production over to the clone. That keeps the
Terraform-managed instance as the source of truth. For a larger loss, the alternative is to repoint the release
at the clone (`helm upgrade --set database.host=<clone IP>`), then import the clone into Terraform.

## What the drill changed

- **`gcloud sql instances clone` gives up after 10 minutes, but this clone took 24.** The script now starts the
  clone with `--async` and polls until the instance is `RUNNABLE`. It can also resume an interrupted drill with
  its original clock (`RESUME_*` variables), which is how this run was finished.
- **Deleting the clone straight after creation failed** with HTTP 409, because its first backup was still
  running. The script now retries until the instance is free.
- **The recovery time is dominated by clone creation.** On a database this size that floor is about 20 minutes.
  If an RTO well under 30 minutes matters, keep a warm cross-zone replica (Cloud SQL HA, Module C1); for a
  failure (not a mistake), failover takes seconds.
