# Drill: internal HTTPS at the Gateway (Module C7)

**Date:** 2026-10-23 · **Release:** 0.1.10 · **Result: passed:** HTTPS from a private CA, end to end.

## What changed

| Before (Part B) | After (C7) |
|---|---|
| `http://gatekeeper.localhost:8088`, `http://auth.gatekeeper.localhost:8088` | `https://gatekeeper.enclave.internal`, `https://auth.enclave.internal` |
| `*.localhost` names, so browsers would accept Keycloak's `Secure` cookies over HTTP | real internal names: HTTPS makes `Secure` cookies work on any name |
| no TLS anywhere | TLS terminated at the internal load balancer |

- **Certificates:** `terraform/modules/tls` creates a private CA (ECDSA P-256, 3 years) and a 90-day server
  certificate for both names. They are uploaded as a **regional SSL certificate**, which the GKE Gateway uses by
  name (`networking.gke.io/pre-shared-certs`), so the private key is never in the cluster.
- **Trust:** the backend trusts the CA through a bundle of the system roots plus the CA, built by an init
  container and pointed to by `SSL_CERT_FILE`. OpenSSL, httpx and urllib all read it, and Google APIs still verify
  against the public roots.
- **DNS:** a private Cloud DNS zone, `enclave.internal`, points both names at the Gateway's VIP, so the browser
  and the backend use one issuer URL. Both names are one site, so the SAML login cookie survives Keycloak's POST.

## What went wrong on the way

1. **The installer found no certificate.** The bastion's identity couldn't list SSL certificates, so Helm refused
   to render (`gateway.tls.preSharedCert is required`). Nothing changed and 0.1.8 kept serving. Fix: a custom role
   with only `compute.regionSslCertificates.get/list`. The installer now stops with a clear message if the lookup
   is empty.
2. **0.1.9 broke every login (500).** The CA ConfigMap was rendered without YAML's `|` block marker, so the PEM's
   line breaks were folded into spaces. OpenSSL skipped the broken certificate without complaint, and every call
   to Keycloak failed verification. Fixed in 0.1.10, with a chart test that the certificate keeps its line breaks.
3. **The DNS zone was replaced in place.** The cutover from `*.localhost` to `enclave.internal` briefly broke
   logins on the release still running until the new one was installed. That's acceptable for a planned change;
   for a live system, create the new zone alongside the old one first.

## For an operator's browser

On the laptop, `/etc/hosts` must send both names to the tunnel, and the browser must trust the CA. Both are system
settings, so the operator does them:

1. Add `127.0.0.1 gatekeeper.enclave.internal auth.enclave.internal` to `/etc/hosts`.
2. Trust `config/internal-ca.pem`: Keychain Access → System → import → "Always Trust" (macOS).
3. Open the tunnel. Port 443 locally needs sudo:

   ```bash
   sudo gcloud compute ssh bastion --zone us-central1-a --tunnel-through-iap -- -N -L 443:10.10.0.100:443
   ```

4. Browse to `https://gatekeeper.enclave.internal`.

Production would issue from Certificate Authority Service (an HSM-backed CA with audited issuance), and devices
would get the CA through the organization's device management.
