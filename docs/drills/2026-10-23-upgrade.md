# Drill: upgrade and rollback under load (Module C2)

**Date:** 2026-10-23 · **Script:** [`proof/upgrade-drill.sh`](../../proof/upgrade-drill.sh) (bastion) with
[`proof/k6/availability.js`](../../proof/k6/availability.js)
**Result: passed on the second attempt:** zero failed requests through an upgrade and a rollback.

k6 sent 20 requests a second through the real Gateway for the whole of each step. The requests cycled through
the frontend, the API's database readiness check, the API's JWKS and Keycloak's discovery document. The upgrade
was the normal bundle install: verify, push to Artifact Registry, copy secrets, `helm upgrade`, `helm test`.

## Attempt 1: 0.1.4 → 0.1.5, then rollback: failed

| Step | Requests | Failed | Which |
|---|---|---|---|
| Upgrade | 4,800 | 10 (0.21%) | all Keycloak discovery |
| Rollback | 3,600 | 17 (0.47%) | all Keycloak discovery |

The frontend and the API had zero failures both times. **Keycloak was restarted by a release that didn't change
it.** Every pod template carried `app.kubernetes.io/version`, so each release changed every template and rolled
every Deployment. Keycloak is a single replica with its database in the pod, it had no graceful drain, and it
used the default rollout, so the switch dropped requests.

Also found: `helm rollback --wait` never returned. Helm 4 waits on every resource in the release, including GKE's
custom resources (PodMonitoring and the load balancer policies), which never report "ready" in its terms.

## Fixes (release 0.1.6)

- **Pod templates carry no version or chart label.** Those stay on the objects, so a release restarts only the
  components it actually changes.
- **Keycloak rolls like the others:** surge first (`maxUnavailable: 0`), then a `preStop` drain so the load
  balancer stops routing to the old pod before it exits.
- **The drill waits on `kubectl rollout status`** instead of `helm rollback --wait`.

0.1.6 was installed once as the transition, unmeasured: it changes every pod template one last time.

## Attempt 2: 0.1.6 → 0.1.7, then rollback: passed

0.1.7 adds a `/version` endpoint (backend) and is a new image tag for the frontend.

| Step | Duration of the change | Requests | Failed | p95 | Max |
|---|---|---|---|---|---|
| Upgrade 0.1.6 → 0.1.7 | 155 s | 4,800 | **0** | 9 ms | 1,138 ms |
| Rollback 0.1.7 → 0.1.6 | 83 s | 3,601 | **0** | 9 ms | 1,691 ms |

Keycloak's pod was 91 minutes old afterwards: untouched by both. The backend (3 replicas) and frontend
(2 replicas) were replaced twice each.

## Why it works

- **Rolling updates add before they remove:** `maxSurge: 1`, `maxUnavailable: 0`.
- **Readiness gates traffic:** a new backend gets traffic only once `/ready` sees the database.
- **Terminating pods keep serving for `drainSeconds` (15 s)** while the load balancer takes them out of rotation.
- **The schema is migrated before new code starts.** The setup hook is `pre-upgrade`, and migrations only expand
  (migration 010 added a nullable column), so old pods keep working against the new schema. A rollback leaves the
  expanded schema in place, which the old code ignores.
- **PodDisruptionBudgets** let a drain take only one replica at a time.

## Check yourself

Renaming a column in one release breaks a rolling update. For a while, old pods querying the old name and new
pods querying the new name run against the same database. One of them is always wrong, and a rollback can't undo
the rename. Expand (add the new column), migrate the data, switch the code, and contract (drop the old column)
only in a later release.
