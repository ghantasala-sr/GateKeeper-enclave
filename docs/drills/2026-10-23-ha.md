# Drills: node drain and database failover (Module C1)

**Date:** 2026-10-23 · **Release:** 0.1.7 · **Script:** [`proof/ha-drill.sh`](../../proof/ha-drill.sh) (bastion)
**Setup:** `terraform apply -var ha=true`: one e2-standard-2 node in each of us-central1-a/b/c, and Cloud SQL
`REGIONAL` (primary us-central1-a, standby us-central1-b). Switched back to zonal afterwards (`ha=false`).

## 1. Drain a node under load: passed (second attempt)

k6 ran at 20 requests a second through the Gateway (frontend, API readiness, JWKS, Keycloak discovery) while the
node holding the most backend/frontend pods was drained.

| Attempt | Node | Requests | Failed | Notes |
|---|---|---|---|---|
| 1 | zone b | 4,800 | 780 (16%) | 700 of them Keycloak, on a node that **wasn't** drained |
| 2 | zone a | 4,801 | **0** | drained in 124 s, p95 7 ms, max 146 ms |

**Why attempt 1 failed.** It started minutes after HA mode had added zones b and c, and after a rollout had moved
pods into them for the first time. GKE's internal load balancer reaches pods through one endpoint group per zone,
and the new zones' groups were still being programmed. Idle checks right afterwards were all 200, and attempt 2
had no failures.

**Lesson:** after adding zones, or the first time pods land in a zone, wait for the load balancer to report every
backend healthy before disruptive work. The runbook says so.

The PodDisruptionBudgets worked as intended. The drain was refused permission to evict a second backend until its
replacement was ready ("Cannot evict pod as it would violate the pod's disruption budget"), then continued.

## 2. Cloud SQL failover: passed

`gcloud sql instances failover enclave-pg` was run from an admin's machine, while the bastion checked the backend
pods' readiness every second.

| Time (UTC) | Event |
|---|---|
| 21:30:17 | Failover accepted (primary us-central1-b → us-central1-a) |
| 21:30:45 | No backend ready: the database is unreachable, so `/ready` fails and pods leave the load balancer |
| 21:34:23 | All backends ready again |
| 21:34:54 | Failover operation reported done (277 s in total) |

- **Not-ready window:** 218 s, about the length of the failover operation itself. On a shared-core `db-f1-micro`
  instance Cloud SQL failovers are slow; dedicated-core tiers usually take about a minute.
- **Restarts:** none (`[0 0 0]` before and after). Liveness checks only the process, so a database outage takes
  pods out of traffic instead of restarting them. When the database came back on the same private IP, the
  connection pool recovered by itself.
- **During the window:** the frontend and Keycloak kept serving, and API calls answered 503.

Also found:
- **Cloud SQL refuses a second failover for a few minutes** after the first (HTTP 409) while the new standby
  syncs.
- **A drill that kills its own watchers by name kills its SSH session:** `pkill -f` matched the remote command
  line. The watcher now starts from a small launcher script.

## Not covered: Keycloak

Keycloak runs one dev-mode replica with its database inside the pod. It survives node drains elsewhere and app
upgrades (see the upgrade drill), but losing its node means a gap in logins until it restarts, about 60 s. Making
it highly available needs Keycloak in production mode on its own Cloud SQL database, with 2+ replicas clustered
over a headless Service. That's a production requirement (see `DEPLOYMENT.md`).
